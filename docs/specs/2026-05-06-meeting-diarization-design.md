# Meeting Diarization Design

## Summary

This design adds speaker diarization to meeting transcription in QuickMeeting. The feature should produce a structured transcript sidecar as the canonical source of truth, generate a human-readable Markdown transcript grouped by speaker blocks, and allow users to rename detected speakers after transcription completes.

The first version limits editing to speaker display names only. Transcript text remains generated by the transcription pipeline and is not manually editable in the app.

## Scope

### In Scope

- automatic speaker diarization as part of the existing meeting transcription flow
- structured transcript persistence for speaker metadata and segments
- Markdown transcript output with basic formatting
- user editing of speaker display names after transcription
- regeneration of transcript artifacts when speaker names change
- retranscription replacing prior diarization artifacts

### Out Of Scope

- manual editing of transcript text
- automatic mapping of speakers to calendar attendees or real identities
- multiple simultaneous transcription jobs
- exporting alternate transcript formats beyond the app-managed Markdown artifact
- speaker rename history or conflict resolution
- partial transcript edits without full artifact regeneration

## Product Decisions

- The app should keep a structured transcript sidecar as the canonical diarization data.
- The user-facing transcript artifact should be Markdown instead of plain text.
- Markdown should default to speaker-block formatting rather than timestamped dialogue lines.
- Users may rename detected speakers, but may not edit transcript text in this version.
- Speaker identities should start as anonymous labels such as `Speaker 1`, `Speaker 2`.
- The feature should integrate into the existing manual transcription entry point in meeting detail.

## Architecture

The diarization feature should extend the existing transcription pipeline rather than creating a separate workflow. `TranscriptionService` remains the single app-facing orchestration boundary and continues to own validation, meeting status updates, model resolution, progress tracking, and final persistence.

The transcription pipeline should become a two-stage process:

1. speech-to-text produces a `TranscriptionResult` with timed segments
2. a diarization stage assigns stable speaker identifiers to those segments

After those stages complete, `TranscriptionArtifactWriter` should persist:

- `transcript.json` as canonical structured transcript data
- `transcript.md` as the derived readable artifact

Speaker renaming should not rerun transcription. Instead, a focused transcript persistence path should update the structured sidecar and regenerate the Markdown artifact from canonical data.

This keeps diarization isolated from UI concerns, avoids parsing Markdown back into application state, and preserves a clean upgrade path for future diarization engines or transcript presentation changes.

## Components

### TranscriptionService

`TranscriptionService` should continue as the app-facing entry point. It remains responsible for:

- validating that the meeting can be transcribed
- enforcing the single-active-transcription rule
- resolving the selected transcription model
- marking the meeting as `transcribing`
- invoking speech-to-text and diarization in sequence
- writing final artifacts
- marking the meeting `completed` or `failed`

The service should not own speaker-label formatting, Markdown rendering, or sidecar mutation details.

### WhisperTranscriptionBackend

`WhisperTranscriptionBackend` should continue returning `TranscriptionResult` with timed segments. It does not need to own speaker display labels or Markdown generation.

This keeps the backend boundary stable and allows diarization strategy changes without redesigning the speech-to-text contract.

### TranscriptDiarizing

A new diarization boundary should be introduced, such as `TranscriptDiarizing`. It should accept the meeting audio URL plus the base `TranscriptionResult` and return a new `TranscriptionResult` whose segments have stable `speakerID` values.

Responsibilities:

- assign stable speaker identifiers like `speaker-1`, `speaker-2`
- preserve segment text and timing from transcription
- avoid UI-specific naming decisions beyond generating default anonymous labels

This boundary should be independent from `TranscriptionService` so diarization behavior can be tested and swapped separately.

### TranscriptionArtifactWriter

`TranscriptionArtifactWriter` should become the sole artifact-rendering component for transcript persistence. It should write both structured and readable artifacts from canonical transcript data.

Responsibilities:

- write `transcript.json`
- write `transcript.md`
- derive transcript preview text
- keep artifact generation deterministic so speaker renames can regenerate output safely

Markdown rendering should be fully derived from structured transcript data rather than hand-edited or partially patched.

### Transcript Persistence For Speaker Renames

A focused transcript persistence helper should be added for post-transcription speaker renames. This design refers to it as `MeetingTranscriptStore`, and its responsibilities should cover:

- loading the structured transcript sidecar
- updating speaker display names only
- rewriting `transcript.json`
- regenerating `transcript.md`
- returning updated preview information if needed

This work should stay out of SwiftUI views so file consistency and failure handling remain centralized and testable.

### MeetingStore

`MeetingStore` should continue storing meeting lifecycle state and file references. `Meeting` should not store structured transcript data or speaker metadata directly.

The main indexed meeting fields remain:

- `status`
- `audioFilePath`
- `transcriptFilePath`
- `transcriptPreview`
- `updatedAt`

`transcriptFilePath` should now point to `transcript.md`.

## Data Model

### Meeting Persistence

The `Meeting` model remains a lightweight index into artifacts on disk. No structured transcript segments, speakers, or diarization metadata should be added directly to `Meeting` in this version.

### Structured Transcript Sidecar

The new canonical sidecar should be persisted as `transcript.json` inside the meeting folder. It should contain enough information to regenerate the Markdown transcript without rereading model output or parsing Markdown.

Conceptually:

- transcript-level metadata
- `speakers: [TranscriptSpeaker]`
- `segments: [TranscriptSegment]`

Suggested shapes:

- `TranscriptSpeaker`
  - `id: String`
  - `displayName: String`

- `TranscriptSegment`
  - stable `id`
  - `text`
  - `startTime`
  - `endTime`
  - `speakerID`

Default speaker labels should be generated from stable speaker ordering, for example `Speaker 1`, `Speaker 2`.

### Markdown Transcript Artifact

The readable transcript artifact should be persisted as `transcript.md` in the meeting folder.

The format should use speaker-block grouping:

```md
## Speaker 1
Hello everyone.

## Speaker 2
Thanks, let's start.
```

Consecutive segments from the same speaker should be merged into the same rendered block when practical so the Markdown reads like meeting notes rather than raw segment dumps.

### Preview Text

`transcriptPreview` should be derived from canonical transcript content, not stored independently in the sidecar as authored UI state. The preview should remain a short leading excerpt of the generated transcript text and should not depend on Markdown heading syntax.

## Data Flow

### Transcription Flow

1. The user starts transcription from meeting detail.
2. `TranscriptionService` validates meeting state, installed model state, and audio file presence.
3. `TranscriptionService` marks the meeting as `transcribing` and starts app-wide progress tracking.
4. `WhisperTranscriptionBackend` returns a base `TranscriptionResult` with transcript text and timed segments.
5. `TranscriptDiarizing` assigns stable speaker IDs to the segments.
6. `TranscriptionArtifactWriter` writes `transcript.json` and `transcript.md`.
7. `MeetingStore` saves the `transcript.md` path plus preview and marks the meeting `completed`.
8. Progress tracking is cleared.

### Speaker Rename Flow

1. The user edits a speaker display name in the meeting detail UI.
2. The transcript persistence helper loads `transcript.json`.
3. It updates only the matching speaker display name.
4. It rewrites `transcript.json`.
5. It regenerates `transcript.md` from the updated structured transcript.
6. The meeting detail view reloads the transcript artifact from disk.

This flow should not alter segment IDs, segment text, or segment timing.

### Retranscription Flow

Retranscription should behave the same as the current replace-transcript workflow, but now both `transcript.json` and `transcript.md` should be replaced as part of the job. Prior speaker renames are discarded when a new transcription is run because the transcript is regenerated from new canonical pipeline output.

## UI Integration

The first UI integration point should remain the meeting detail screen.

Expected behavior:

- completed transcripts should render from `transcript.md`
- the detail view should expose speaker names derived from the structured sidecar
- users should be able to rename speakers after transcription completes
- speaker rename controls should affect only display names, not transcript text
- meetings with missing readable artifacts should degrade gracefully rather than crashing

The exact UI layout can follow existing meeting detail patterns, but the design should preserve a clear distinction between:

- transcript reading from Markdown
- speaker metadata editing from the structured sidecar

No general-purpose Markdown editor should be introduced in this version.

## Storage And Artifact Layout

Artifacts should live beside `audio.wav` in the existing meeting folder:

- `<meeting folder>/audio.wav`
- `<meeting folder>/transcript.json`
- `<meeting folder>/transcript.md`

The structured sidecar is canonical for transcript regeneration. The Markdown artifact is derived and user-facing. The meeting record should reference the Markdown artifact path.

## Error Handling

The existing transcription failure rules should remain in force:

- source `audio.wav` is never deleted automatically
- if a started transcription fails, the meeting becomes `failed`
- progress tracking is cleared whether transcription succeeds or fails
- user-facing service errors should come from the orchestration layer, not backend implementation details

Additional diarization-specific rules:

- `transcript.json` and `transcript.md` should be treated as an atomic pair from the app's perspective
- if either artifact write fails, the transcription job should fail
- speaker rename should fail without mutating visible state if rewriting the sidecar or Markdown artifact fails
- missing or unreadable sidecar data should disable speaker rename controls gracefully

The implementation should prefer writing complete replacement artifacts over in-place partial mutation so failed writes do not leave mixed generations behind.

## Testing

Tests should cover the orchestration boundary, artifact generation, and rename behavior.

### Core Success Cases

- transcribing a recorded meeting writes both `transcript.json` and `transcript.md`
- `Meeting.transcriptFilePath` points to `transcript.md`
- transcript preview is derived and stored on the meeting
- meeting status changes from `recorded` to `transcribing` to `completed`

### Markdown Rendering

- Markdown groups transcript output into speaker blocks
- default speaker labels render as `Speaker 1`, `Speaker 2`
- consecutive segments for the same speaker render into readable grouped output

### Rename Behavior

- renaming a speaker updates only the speaker display name
- renaming regenerates both structured and Markdown artifacts
- renaming does not modify segment IDs, text, or timings

### Retranscription

- retranscription replaces prior structured and Markdown artifacts
- retranscription discards prior renamed speaker labels in favor of fresh pipeline output

### Failure Cases

- diarization failure marks the meeting `failed`
- failure to write either transcript artifact marks the meeting `failed`
- progress tracking is cleared after success and failure
- missing or unreadable sidecar content degrades gracefully in the meeting detail UI

## Rollout Notes

This feature should be implemented as an extension of the current transcription pipeline rather than a separate migration-heavy subsystem. The most important design constraint is preserving a single canonical structured transcript source while making Markdown the user-facing artifact.

That separation keeps rename behavior safe, makes retranscription predictable, and leaves room for future improvements such as alternate diarization engines, richer transcript formatting, or playback-linked transcript navigation.
